## 根因（四条，均在分析/呈现层）

### ① 64% 的检查项结论是模板套话 —— 主因

`plugins/sqlserver/presentation.py:886 _inject_analysis()` 用一个 `(section_id, title 关键字) → rule_id` 的映射表，把 findings 塞回对应检查项。**没命中规则的检查项直接 `continue`**，于是走渲染层的兜底文案。

实测 42 个检查项的结论分布：

- 有实质结论 **15 个**（都是命中了规则的）
- 模板套话 **27 个**（`已采集并展示本项巡检事实，不单独形成风险判断。`）

典型案例（同一条 SQL Server 报告里）：

| 检查项 | 结论 | 评价 |
|:---|:---|:---|
| 实例基础信息 | 已采集并展示本项巡检事实，不单独形成风险判断。 | 套话，没说采到了什么版本/补丁/启动时间 |
| 数据库大小汇总 | 已采集并展示本项巡检事实，不单独形成风险判断。 | 套话，没说总容量、增长趋势 |
| 主要等待 | 已采集并展示本项巡检事实，不单独形成风险判断。 | 套话，没说 top 等待类型是什么 |

MySQL 同位置（`plugins/mysql/presentation.py`，42 处 `self._item(...)` 调用，每处独立写结论）：

| 检查项 | 结论 |
|:---|:---|
| 主机与操作系统信息 | 已取得数据库主机、操作系统、CPU 和内存基本信息；本实例为本地采集，系统指标可用于关联分析。 |
| 文件系统容量 | 已取得主要文件系统容量；个别失效挂载点读取失败，不影响已展示挂载点。 |
| 内核错误摘要 | 未发现内核错误级别日志。 |
| 磁盘现场指标 | 现场短时窗口内磁盘 util 和 await 整体较低，未发现持续 I/O 饱和；需结合数据目录映射与高峰历史复核。 |
| 文件 I/O Top | 已取得 Performance Schema 文件 I/O 累计统计；该数据为实例启动以来累计值，不等同于当前实时吞吐。 |

差别很明确：MySQL 的正常项也把**采到了什么、这份数据回答什么问题、边界在哪**说清楚，而且带条件分支（有数据/没数据两套文案）和实测数字（`f"共 {len(schemas)} 个 Schema"`）。

### ② 42 个检查项的 `display.note`（口径说明）全空

`display.note` 渲染成表格下方那行「说明：……」，用于交代**截断规则、排除项、判定口径**。实测：

- SQL Server：`presentation.py` 里 `note` 出现 **0 次**，模型 42/42 项 note 为空。
- MySQL：`presentation.py` 4 处填充（`L574` / `L1907` / `L2355` / `L2464`），报告里体现为十几条说明行，例如：
  - 「说明：已排除 5 个 tmpfs/devtmpfs/光驱等非持久化挂载点」
  - 「说明：仅展示 ACTIVE 插件，最多 30 行。正文展示前 20 条，共 30 条；完整明细保留在分析结果中。」
  - 「说明：列名为节点 IPv4 末位；判定口径为 达标 / 不达标 / 不适用，「不适用」表示该参数在当前角色或拓扑形态下没有判定语义」

**最后一类对交付质量影响最大**：不写「正文展示前 N 条，共 M 条」，客户就无从知道报告里的表是不是全量。

### ③ `health_assessment.scoring_policy = null` → 首页没有「结论速览」

`inspection_core/word_engine.py:906` 首页「结论速览」note_box 的开关是：

```python
if score is not None and base:      # base 来自 health_assessment.scoring_policy["base"]
```

SQL Server 模型里 `scoring_policy = null`，整段被跳过。MySQL 有该字段，于是首页出现一段 274 字的说明——把**健康分怎么算的、扣了多少分、风险分布在哪几个节点、有几项证据缺口**一次讲清。

当前 SQL Server 报告首页只有两张小表（`5x3` + `5x3`），**没有任何解释性文字**。

### ④ 单实例不出「高风险项速览」

`word_engine.py:1018` 的速览表要求 finding 带 `node` 键（多实例时才注入）：

```python
if str(finding.get("severity")) == "high" and finding.get("node")
```

MySQL 是三节点 → 有 node → 首页出现「1.2 高风险项速览」（`节点|风险项|关键事实`）。SQL Server 单实例 → 速览表被跳过。这是**共享层对单实例场景的覆盖缺口**，三个库都会遇到。

## 附带确认：不是「换个布局」能解决的

做了一次对照实验：同一份模型分别用两种布局生成。

| 布局 | 正文文字量 | 表格文字量 | 总文本量 | 表格数 | 章标题 | 待客户确认事项 | 综合结论与管理建议 | 证据索引 |
|:---|---:|---:|---:|---:|:---:|:---:|:---:|:---:|
| `professional`（当前默认，现报告在用） | 8,844 | 30,375 | 39,219 | 76 | 19 | 有 | 有 | 有 |
| `legacy`（v31） | 16,426 | 15,504 | 31,930 | 56 | 16 | **无** | **无** | **无** |

`legacy` 字数确实上来了，但它是**另一种取舍**——逐项展开分析结论，代价是丢失章节：

- 丢「待客户确认事项」独立章
- 丢「综合结论与管理建议」独立章（被并进风险章）
- 丢附录「证据索引」
- 整改计划从 6 列收成 3 列

而且 MySQL 报告本身用的就是 `professional`（有「2.3 巡检方法与报告边界」「本章分析结论」「16.3 规则执行状态」「16.4 证据索引」），**不是 legacy**。

→ **正确做法是把数据补进 `professional` 路径，而不是切换布局。**

| 档 | 内容 | 位置 | 影响 | 风险 |
|:---|:---|:---|:---|:---|
| **P0-1** | 42 个检查项逐个补写 `analysis.conclusion`（正常项也说清采到了什么、边界在哪），未命中规则时由 `_inject_analysis` 保留手写结论 | `plugins/sqlserver/presentation.py:_build_sections` | 正文预计 +3,000~4,000 字，追平 MySQL | 纯文案，无判据改动；需补守门测试防回归成套话 |

口径固定并已脚本化：`tools/report_text_stats.py`（正文文字量 = 总文本量 − 表格文字量）。样本是**同一份 9/24 采集包**（`sqlserver_inspection_v1_192.168.100.129_db-sql-01_1433_20260924_013803.zip`，46 个采集模块），只重跑生成代码。

正文文字量已超过 MySQL（8,844 vs 6,028）。**总文本量仍低于 MySQL 是结构性的，不是缺陷**：MySQL 那份是三节点集群，风险登记册、P1~P3 整改计划、证据索引都按节点数放大（表格文字量 62,081 是 SQL Server 的 2 倍即由此而来）；折算到单节点后，SQL Server 单实例明显更厚。

### 交付物与源包的对应关系（踩过一次）

`analysis_output/` 下的报告只由 `analyze.py <包> -o analysis_output` + `generate_report.py analysis_output` 两步产出，**中间产物（`analysis.json` / `report_model.json`）不落库**。于是有两种悄悄出错的路径：

1. **只重跑 `generate_report.py`、不重跑 `analyze.py`** → 报告的正文是新代码渲染的，但底下的 `report_model.json` 是上一次分析留下的，数据与结论都可能过时。
2. **用错采集包** → 本机有两份同实例的包，报告封面写「巡检日期 2026-09-24」，对应的是项目根目录的 `sqlserver_inspection_v1_192.168.100.129_db-sql-01_1433_20260924_013803.zip`（46 个模块 / 53 个顶层键）；`D:\inspection\sqlserver_inspection_v1_db-sql-01_20260728_000158.zip` 是更早的 7/28 包（38 个模块 / 45 个键）。用错包会让发现项从 30 条掉到 20 条、健康分从 0 变成 6 —— 看起来「报告变好了」，实际是换了数据。

改完代码重出报告时，**两步都要跑，且源包要与报告封面日期一致**。

### 四条改动

| 档 | 改动 | 落点 |
|:---|:---|:---|
| **P0-1** | 新增 `plugins/sqlserver/analysis_text.py`（1,866 行）：60 条 `(section_id, title) → 结论文案` 注册项，每条含**实测数字**与**口径边界**；由 `_build_sections` 末尾的 `decorate_sections()` 统一施加 | 新模块 + `presentation.py` 2 行接线 |
| **P0-2** | 同上，每条注册项同时产出 `display.note`；另加自动截断提示（模块原始行数 > 正文渲染行数时补「正文展示前 N 条，共 M 条」） | 同 P0-1 |
| **P0-3** | `metrics.SEVERITY_WEIGHTS` 提为单一来源；`presentation` 的 `health_assessment` 补 `counts` + `scoring_policy`；`report_adapter` 透传 | `metrics.py` / `presentation.py` / `report_adapter.py` |
| **P1-2** | 新增「待客户确认事项」模板表（30 条规则）+ `pending_confirmations()`，由已触发规则派生 | `analysis_text.py` + adapter 透传 |

**共享层改动一处**：`word_engine.build_summary_v31` 原先把 `critical` 并入 `high` 计算扣分。SQL Server 的 critical 权重是 18、high 是 10，合并会让首页算式与实际分数对不上。现改为「policy 里有 `critical` 档就单独算，没有则退回合并」—— MySQL 的 severity 体系里没有 critical，其 policy 也就没有这一档，**输出逐字不变**（`test_word_engine.py` 的 hash 校验通过即为证）。

### 落地时新发现的根因：链路断在适配器

`report_adapter.adapt_report_model()` 是**重建**模型对象而不是透传 —— 它自己拼 `health_assessment`，只取 `severity_counts`，于是：

- 分析层新写的 `scoring_policy` 被丢掉 → 首页「结论速览」仍然不出现（第一次出报告时「结论速览」「待客户确认事项」整段消失，就是这个原因）；
- `pending_confirmations` 根本没被读取。

这与之前发现的「附录规则执行状态三行恒 0」（adapter 由 findings 反推 evaluations）是**同一类缺陷**：适配器不认识的键会被静默丢弃，分析层写得再对也到不了报告。已补两个透传 + 一个「缺字段必须保持 None」的守门测试。

### 验证

- 新增守门测试 `tests/test_sqlserver_report_text.py`（20 项 / 30 subtests），四类断言：**静态结构对账**（`presentation.py` 声明的检查项 ⇄ 文案注册表，双向无缺无余，AST 提取不依赖运行数据）、**运行时覆盖**（真包每个渲染项都要有结论 + 依据 + 口径说明，且不得出现旧兜底套话）、**口径一致**（`scoring_policy` 权重必须等于 `SEVERITY_WEIGHTS`）、**待确认清单**（模板规则号必须真实存在；技术性整改项不得进表；同规则去重；无 findings 时给空列表而非 None）。
- **反向验证**：逐条破坏 13 处修复点，全部被守门测试抓住，文件逐字节复原（`_work/_revcheck_text.py`）。
- 全量 pytest：**5 failed / 265 passed / 130 subtests**，5 项与改前逐条同名（MySQL 侧源包缺失，预存在）→ **零新增回归**。
- 报告首页现在实测输出：`总体健康分 0/100：以 100 分为基线，按严重 1 项、高风险 4 项、中风险 9 项、低风险 16 项分别扣 18、10、4、1 分，合计扣 110 分，扣分已触及 0 分下限 —— 该分数表示风险项数量超出评分区间，不代表系统当前不可用。`（1×18+4×10+9×4+16×1 = 110，可逐项核对）

## 落地结果（及格线三条，2026-10-09）

拿外部参考报告《某三甲医院 SQL Server 巡检报告》做了一轮「这份报告能不能直接交出去」的复核。
结论分两个坐标轴看：**加分题**（缺采集项，例如没有「建议值」列、IO 次数没展示）与**及格线**（数据采到了、
判据也判了，坏在呈现层）。本轮只动及格线三条 —— 不是不能做得更详细，是一条都不能少。

### 三条改动

| 档 | 现象 | 根因 | 落点 |
|:---|:---|:---|:---|
| **P1** | 单实例报告整份没有「高风险项速览」 | 共享引擎的筛选条件带 `and finding.get("node")`，而 `node` 键**只在多实例输入时注入** → 单实例恒空、整节不渲染 | `inspection_core/word_engine.py`（**共享层，四库通用**） |
| **P2** | 6 个检查项在「采集成功但确认无数据」时**整项消失** | `presentation.py` 用 `if rows:` 包住 `append(...)`；空数据 = 这一项从报告里彻底不见，读者无法区分「查了没有」与「没查」 | `plugins/sqlserver/presentation.py` |
| **P2** | 参数分析结论句丢主语，读者会读错 | `_inject_analysis` 把一个检查项命中的多条规则拼进同一格，各条依据/建议不带主语 | `plugins/sqlserver/presentation.py` |

### P1 的两个细节

- **筛选口径必须与首页一致**：首页「结论速览」把 `critical` 算进高风险档。速览若只挑 `high`，就会出现
  「首页写 5 条、速览列 4 条」的自相矛盾。故筛选改为 `severity in {"critical", "high"}`。MySQL 的严重度
  体系里没有 `critical` 档，这条改动对那边**等价于原逻辑、输出不变**。
- **本节的资格与节点数无关**：它只回答「最要紧的事情有没有被放在第一页」，所以删掉 `node` 条件是对的，
  不是给单实例打补丁。
- **硬编码章节号必然出错**：口径原文写死「见第 12 章」，而风险登记册在 MySQL 是第 12 章、**SQL Server 是第 17 章**
  （本报告实测第 17 章）。改为「见**风险登记册**章节」。
- 表头不再固定带「节点」列：仅当确实存在多实例时才加，单实例输出 `风险项 / 关键事实` 两列。

### P2 的关键约束：「采集成功、确认没有」≠「没采到」

两者是**完全相反**的结论，不能在报告里长得一样，更不能一起消失 —— 与既有规矩「**未采集 ≠ 0**」同源。

于是新增模块级 `_blank_note(collection, confirmed)`，按 `collection.status` 分叉：

- `success_no_data` → 说「已检查…本次未发现…」；
- 其余（`not_evaluated` / `skipped` / `permission_denied` / `error` / 缺字段）→ 说
  「**本项未完成评价（未采集或采集不完整），不能据此判定为没有问题。**」

> 这条是踩出来的：初版把 6 项的 `empty_text` 全写成「已检查…未发现」，而其中「陈旧统计信息」「索引碎片」
> 「孤立用户」三项实际状态是 `not_evaluated`（深度检查未启用）—— 那就成了一句客户会当真的**假话**。

涉及的 6 项：`缺失索引候选`、`未使用索引`、`陈旧统计信息`、`索引碎片`、`可疑页面`、`孤立用户`。
配套在共享引擎加 `display.empty_text` 支持（item 可自带更准确的空数据文案，未带时才退回通用措辞）。

### P2 主语归属

`_label()`：仅当一个检查项命中**多条**规则时才给依据/建议加 `object_name：` 前缀，且值本身已以该名字开头时不重复加。
单条规则不加（加了是噪音）。实测改前那句会串成：

```
max server memory=2147483647 MB（默认值，未配置），物理内存=4095 MB；当前值=5；…
```

那个「当前值=5」是 `cost threshold for parallelism` 的，读者会读成最大内存配了 5 MB。改后：

```
…；cost threshold for parallelism：当前值=5；blocked process threshold (s)：value_in_use=0（建议 >= 30）；
建议：max server memory：…；cost threshold for parallelism：…；blocked process threshold (s)：…
```

## 落地结果（第 1 章着色补强，2026-10-09）

用户在 Word 里看到「风险」没标红。逐 run 读交付 docx 的字色后，结论分两半：
**「风险」本来就是红的**，缺口在别处。

### 着色前的实测（读 run 级 `font.color` 与单元格 `w:shd`）

| 位置 | 实测字色 | 底纹 | 判定 |
|:---|:---|:---|:---|
| 首页计数表「高风险 5」 | `#111111` 常规 | 无 | **没着色** |
| 1.1 综合结论 · 状态列「风险」 | `#9B1C1C` 加粗 | 无 | 已着色 |
| 1.1 综合结论 · 「关注」 | `#B26A00` 加粗 | 无 | 已着色 |
| 1.2 速览 · 5 条风险项名 | `#9B1C1C` 加粗 | 无 | 已着色 |
| 1.3 管理关注 ·「立即处理 5 项」 | `#111111` 常规 | 无 | **没着色** |
| 参照：风险分级 × 节点矩阵 | `#9B1C1C` | `F6DEDE` | 有底纹（**仅 MySQL 产出**） |

所以真正的缺口是两条：① 首页计数表与 1.3 的紧迫度数字**完全没有按档着色的分支**；
② 全篇只有**字色**一种红 —— 底纹机制（`RISK_MATRIX_STYLES`）只被 MySQL 那份多节点报告的
「风险分级 × 节点矩阵」用上，SQL Server 单实例不生成那张表，于是一块底纹都没有。

另外 `#9B1C1C` 是深红（RGB 155,28,28），9.5pt 加粗下容易被读成黑 —— 这是"技术上没错、
体感上确实弱"的那一类。着色代码本身**本批之前就在**（`word_engine.py` 的
`color = COLOR_HIGH if status == "risk" ...` 在 git HEAD 里是上下文行），且改前那份
`_prev_report.docx` 同样是红的，**不是本批改坏的**。

### 五处改动（全在共享层 `inspection_core/word_engine.py`）

| 位置 | 改动 |
|:---|:---|
| 首页计数表 | 四个数字按档给字色：高风险 `9B1C1C`、中风险 `B26A00`、低风险 `6B5A00`，加粗；总分格随「高风险」列同档 |
| 1.1 状态格 | 按 `status` 加淡底纹：`risk` → `EFD2D2`、`attention` → `FBF0DC`；`normal` 不着色 |
| 1.2 风险项名 | 按 `severity` 加底纹：`critical` → `EFD2D2`、`high` → `F6DEDE` |
| 1.3 处置列 | 按 P1/P2/P3 给字色（红/橙/褐）；`P1` 与 `P2` 为空时不着色 |

三条设计约束：

- **为 0 的档不着色** —— 「0 项」看起来像警报是误导。
- **总分格与「高风险」列同档** —— 总分是各档扣完的结果而不是独立判断，同色才能让
  「总分 + 高风险数」被读成一件事。
- **只给「标签格」上底色，不动整行** —— 底色是标签不是背景板，整行染色会压低结论本身的可读性。
- 同一档位在整份报告里**只允许有一个色值**，所以 `SUMMARY_STATUS_FILLS` 从
  `RISK_MATRIX_STYLES` 派生；两处各调一个红迟早会漂移。

### 3.4 改名：内容里没有一个启动参数
